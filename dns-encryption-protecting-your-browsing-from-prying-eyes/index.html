DNS Encryption: Protecting Your Browsing from Prying Eyes

October 22, 2026 · Quiet Wire

Every time a browser looks up a name like example.com, it sends a plain-text request to a DNS resolver. This request can be read by any device on the path – the ISP, a corporate firewall, or a malicious Wi-Fi hotspot. DNS encryption masks these lookups, preventing casual eavesdropping while leaving other connection parts exposed. Below is a breakdown of how the two main protocols work, what they cannot conceal, and how to set them up alongside a VPN.

What is DNS and Why Encrypt It?

DNS (Domain Name System) acts as the internet’s phone book. When you type a URL, your device asks a resolver to translate the domain name into an IP address, typically a four-octet IPv4 value or a 128-bit IPv6 value. The query and its answer travel in clear text over UDP (port 53) or TCP (port 53) unless a protective layer is added.

Because the query contains the exact domain name you are visiting, anyone sniffing the traffic sees a list of your intended destinations. In most residential setups, the ISP runs the first resolver, allowing it to compile a daily log of every hostname you look up. For privacy-focused users, this is a significant leakage vector. Research indicates over 90% of browsers still use unencrypted DNS by default, meaning roughly 99% of everyday web sessions reveal the domain name in clear text.

Encrypting DNS removes that visibility. The query is wrapped in a cryptographic tunnel, so an observer sees only “some DNS traffic” occurring, not the specific name being resolved. This protection is comparable to HTTPS for web pages: the content remains accessible, but the request itself is hidden.

DNS over HTTPS (DoH) Explained

DoH tunnels DNS queries within ordinary HTTPS traffic. From a network perspective, the packets appear as standard web requests to port 443, using the same TLS handshake and HTTP/2 framing.

  • Indistinguishability – Because the payload is encrypted and the outer layer is HTTPS, deep-packet inspection (DPI) tools cannot reliably distinguish DoH from regular browsing. This makes blocking or throttling DoH harder for network administrators.
  • Browser integration – Chrome, Firefox, and Edge offer DoH settings within their native preferences. When enabled, these browsers send all resolution requests to a configured DoH endpoint, falling back to the system resolver only if the HTTPS connection fails.
  • Provider ecosystem – Privacy-oriented DNS operators like Cloudflare and Google publish public DoH URLs (e.g., https://dns.cloudflare.com/dns-query). These URLs are static, versioned, and served over TLS with strong cipher suites (TLS 1.3 is typical).

A practical example: A user on public Wi-Fi enables DoH in Firefox and selects Cloudflare’s endpoint. When the browser looks up news.example.com, the client establishes a TLS-encrypted TCP session to 1.1.1.1:443. It then sends an HTTP GET request with the DNS query encoded in the URL and receives the answer in the HTTP response body. A network monitor observes only “TLS handshake to 1.1.1.1” and “HTTPS GET /dns-query”, not the domain name.

DNS over TLS (DoT) Explained

DoT isolates DNS traffic within its own TLS session on a dedicated port (853). The protocol, defined by RFC 7858, mirrors the security properties of HTTPS but lacks the HTTP framing layer.

  • Dedicated port – Since DoT consistently uses port 853, firewalls can identify the traffic more easily than DoH. However, the TLS layer still encrypts the payload. Some corporate networks deliberately block port 853 to enforce plain UDP DNS, potentially making DoT less reliable on restrictive networks.
  • Strong encryption – DoT implementations typically enforce TLS 1.2 or higher and require forward-secret cipher suites. The client validates the server’s CA-signed certificate, preventing man-in-the-middle attacks.
  • System-wide configuration – Operating systems such as Android 9+, Windows 10 (1709+), and recent Linux distributions include native DoT support. Users can direct the system resolver to a DoT server (e.g., dot.cloudflare.net), allowing all applications relying on the OS resolver to benefit automatically.

In practice, a Linux machine with systemd-resolved configured for DoT opens a TLS session to the resolver on port 853, sends a DNS message wrapped in the TLS record, and receives the encrypted answer. No HTTP headers are involved, reducing overhead compared to DoH. However, the dedicated port can serve as a visibility cue for network filtering.

What DNS Encryption Can’t Hide

Encryption prevents the content of the query from being read but does not make the query invisible to the resolver itself. The resolver you configure – whether Cloudflare, Google, or a self-hosted server – still sees every domain name you request. Privacy therefore depends on the resolver’s logging policy and jurisdiction.

  • Resolver insight – A reputable resolver will maintain minimal logs, often just timestamps and aggregated statistics. You can verify a provider’s policy by reviewing its published privacy statement or checking for third-party audits like SOC 2 Type II.
  • Encrypted Client Hello (ECH) and SNI – Even with DoH/DoT, the TLS handshake reveals the server name you are contacting (SNI). Newer extensions like Encrypted Client Hello aim to hide this value, but adoption is still limited. Until ECH is widely deployed, a passive observer can still infer which DNS provider you are using.
  • VPN interaction – If a VPN routes all traffic through its tunnel, the VPN exit node still receives DNS packets unless the client explicitly forces DNS queries over the encrypted channel within the tunnel. Misconfiguration can lead to “DNS leaks,” where the device reverts to the ISP’s resolver.
  • Website visibility – After a successful DNS lookup, the subsequent TCP/QUIC connection to the target server includes your public IP address. Neither DoH nor DoT hides this IP from the destination site or from any ISP that can observe the flow of encrypted packets to the server’s IP.

DNS encryption is a layer of protection, not a complete shield. It should be used alongside a trustworthy DNS provider and, where possible, a VPN that enforces DNS tunneling.

Configuring DNS Encryption

Platform DoH Support DoT Support Typical Steps
Windows 10/11 Settings → Network → Advanced DNS Settings → Network → Advanced DNS Choose “Encrypted DNS” and enter provider URL or IP address.
macOS (Ventura+) System Preferences → Network → DNS (via UI or networksetup) System Preferences → Network → DNS (via UI or networksetup) Use networksetup -setdnsservers with dns.cloudflare.com and enable “Secure DNS”.
Linux (systemd-resolved) /etc/systemd/resolved.conf (DNSOverTLS=yes, DNS=) Same file (DNSOverTLS=yes) Edit the file, set DNS= to the resolver’s IP, restart systemd-resolved.
Android 9+ Settings → Network → Advanced → Private DNS (hostname) Same UI (enter dns.google) Enter the provider’s hostname (e.g., dns.google).
iOS 14+ Settings → Wi-Fi → Info → Configure DNS (Manual) No native DoT UI Add a DoH server address in the “Configure DNS” section.

Browser-level activation

  1. Chrome – Open chrome://settings/security, enable “Use secure DNS” and select a provider or enter a custom DoH URL.
  2. Firefox – Navigate to about:preferences#privacy, scroll to “Network Settings”, check “Enable DNS over HTTPS” and pick a preset or custom endpoint.
  3. Edge – Go to Settings → Privacy, search, and services, turn on “Use secure DNS to specify how to lookup the network address for websites”.

Router-level configuration

Some modern firmware (e.g., OpenWrt, AsusWRT) includes a “DNS over TLS” option. Entering the resolver’s hostname and port here forces every LAN device using the router’s DHCP-provided DNS to benefit from DoT automatically, provided the devices themselves do not override these settings.

Verification

After configuration, run a DNS leak test. The test site displays the IP addresses of the resolvers it detects. If these IPs match your chosen provider and no ISP addresses appear, the encryption is active. Repeat this check on multiple devices and networks for consistency.

DNS Encryption and Your VPN

Most commercial VPN services operate their own DNS resolvers, accessible only through the encrypted tunnel. When you connect, the VPN client replaces your system’s DNS servers with the provider’s internal addresses.

  • Choose the right mode – Some VPN apps offer a toggle between “Use VPN DNS” and “Use custom DNS.” Selecting the VPN’s own servers ensures DNS queries remain within the tunnel. If you prefer an external DoH/DoT provider, manually configure the client’s DNS settings instead of using the default.
  • Leak protection – A well-implemented VPN binds DNS traffic to the tunnel interface (e.g., tun0). You can verify this by checking the routing table (ip route show) and confirming that DNS server IPs resolve to the VPN’s internal subnet.
  • Policy audit – Review the VPN’s privacy policy for statements on DNS logging. Look for independent audits (e.g., no-logs audits by reputable firms) and understand the jurisdiction under which logs might be compelled. A provider based in a 14-Eyes country may face broader data-sharing requests.

In practice, a user on a Windows machine connects to a VPN advertising “Zero-log DNS.” The client automatically sets the DNS to 10.8.0.1 (the VPN’s internal resolver). The user then uses a leak test to confirm that only the VPN’s IP is visible, ensuring no fallback to the ISP’s resolver occurs.

Key takeaways

  • Encrypting DNS queries with DoH or DoT protects your browsing activity from local network observers and ISPs.
  • DoH uses HTTPS, while DoT uses a dedicated TLS port for encryption.
  • DNS encryption does not hide your destination IP address from the website or your ISP.
  • Ensure your VPN is configured to use encrypted DNS and prevent leaks.

Frequently asked questions

Is DoH or DoT better for privacy?

Both offer strong encryption. DoT is generally considered more secure as it uses a dedicated port, while DoH can blend in better with regular traffic but might be easier for networks to block.

Can my ISP still see what websites I visit with DoH/DoT?

They cannot see the specific DNS queries themselves if encrypted. However, they can still see the IP addresses of the servers you connect to and the volume of traffic.

Do I need DoH/DoT if I’m using a VPN?

Yes, it’s recommended. While a VPN encrypts your traffic, ensuring your DNS queries are also encrypted adds another privacy layer and prevents potential DNS leaks.
